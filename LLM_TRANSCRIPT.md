## NX in 30 seconds

NX is a monorepo build system. Three things it does here:

1. **Project graph** — it scans the repo, finds "projects" (each folder under `packages/` with a `project.json`), and knows how they depend on each other. `nx build X` builds X's dependencies first.
2. **Inferred targets** — this workspace uses NX 22's *plugin inference* ([nx.json](nx.json:4)). You'll notice [packages/pokemon-ui/project.json](packages/pokemon-ui/project.json) has `"targets": {}` — empty. NX sees a `vite.config.ts` in that folder and *infers* `build`/`test`/`serve`/`preview` targets from it. That's why the file looks empty but `nx run pokemon-ui:serve` works. Run `nx show project pokemon-ui --web` to see what it actually inferred.
3. **Caching** — task results are cached in `.nx/`, so unchanged builds are instant.

The `packages/*` folders are also **pnpm workspaces** ([pnpm-workspace.yaml](pnpm-workspace.yaml)), but note: all runtime deps live in the **root** [package.json](package.json). The individual packages have no `package.json` of their own. That's a deliberate "single version policy" setup — one dependency tree, no version drift.

## Tilt in 30 seconds

Tilt is a dev-loop orchestrator for local Kubernetes. A `Tiltfile` is Python (Starlark). It gives you one command (`tilt up`), one dashboard (localhost:10350), and file-watching that rebuilds/redeploys only what changed.

The root [Tiltfile](Tiltfile) just `include()`s three per-service Tiltfiles plus two DB tasks. Three resource types are in play:

| Primitive | Meaning | Used for |
|---|---|---|
| `k8s_yaml` + `k8s_resource` | apply manifests, port-forward | postgres, backend |
| `docker_build` | build an image, wire it into the deployment by image name | backend |
| `local_resource` | run a plain process on your Mac | frontend vite server, migrations |

## How the three pieces actually run

**Postgres** — [tilt/postgres/postgres.yaml](tilt/postgres/postgres.yaml): a Deployment + ClusterIP Service + a 2Gi PVC (data survives `tilt down`). Port-forwarded to `localhost:5432`. Has a `pg_isready` readiness probe, which is what the other resources' `resource_deps` wait on.

**Backend** — runs *in Kubernetes*, and the loop is a two-stage relay:
1. `local_resource('backend: build if changed')` runs `nx watch ... -- nx build pokemon-user-backend`, which writes `packages/pokemon-user-backend/dist/main.js` on your host.
2. The [Dockerfile](packages/pokemon-user-backend/Dockerfile) is a **thin packager** — it does *not* compile. It just `COPY`s that already-built `dist/` in and installs prod deps. Tilt watches the build context, sees `dist/` changed, rebuilds the image, redeploys.

⚠️ **Gotcha to know now**: that build resource is `trigger_mode=TRIGGER_MODE_MANUAL` ([Tiltfile:4](packages/pokemon-user-backend/Tiltfile:4)). It does not auto-start. On a fresh `tilt up` you have to click the ▶ on `backend: build if changed` in the Tilt UI once to kick off the watcher — otherwise backend changes silently never reach the container. That's also why `dist/` is checked into the repo.

**Frontend** — *not* in Kubernetes at all. It's a `local_resource` running the Vite dev server on your host at :4200, straight HMR, no container. Pragmatic choice: k8s round-trips would kill the React feedback loop.

**Migrations** — MikroORM CLI, run as local_resources against the port-forwarded Postgres. `db: migration:up` runs automatically after Postgres is ready; `db: migration:create` is manual (click to run) and diffs your entities against the DB to generate SQL.

## 3. Response

Good instinct to pause there — that's the one decision in the list with real teeth. Let me lay out the implications, because "share the contracts" splits into three very different things:

**Sharing plain types/interfaces — safe.** `type Pokemon = { id: number; name: string; ... }` erases entirely at compile time. Zero bundle cost, zero runtime coupling. Both `vite.config.ts` files already register `nxViteTsPaths()`, so a tsconfig path alias resolves in both apps with no extra plugin work. This is pure upside.

**Sharing `class-validator` DTO *classes* — risky.** Those are real runtime classes with decorators. Sharing them drags `class-validator` and `reflect-metadata` into the browser bundle for something only Nest's `ValidationPipe` uses. It also inverts the dependency: your UI now depends on a backend validation library's version.

**Sharing MikroORM entities — don't.** They carry ORM decorators, `Collection<T>` wrappers, and lazy-loading semantics tied to an `EntityManager`. Serialize them over the wire and the frontend type is a lie about what actually arrives.

The clean line is **types-only shared lib, DTO classes stay in the backend and `implements` the shared interface**. That gives you compile-time enforcement in both directions — if the backend DTO drifts from the contract, `tsc` fails on the backend — without shipping a single byte of backend runtime to the browser.

The other implications worth naming: it's a third project in the graph, so `nx graph` gets a real edge (arguably a feature — it shows the monorepo doing its job), you need one `paths` entry in `tsconfig.base.json` (which currently has none), and you accept that a contract change now touches two apps at once. At this scale that's a benefit, not a cost.

## 1. Getting the 150 — what the API actually returns

**The list call** — `GET /api/v2/pokemon?limit=150&offset=0` — returns exactly 150 results (Bulbasaur #1 → Mewtwo #150), but only `{ name, url }`. No sprite, no types.

**The detail call** — `GET /api/v2/pokemon/{id}` — has everything: `id`, `name`, `types[]`, `stats{}`, `height`, `weight`, `sprites`.

The important find: **sprite URLs are fully deterministic from the id.**

```
https://raw.githubusercontent.com/PokeAPI/sprites/master/sprites/pokemon/{id}.png
https://raw.githubusercontent.com/PokeAPI/sprites/master/sprites/pokemon/other/official-artwork/{id}.png
```

So the cost of your model depends entirely on one field:

| Fields | HTTP calls needed |
|---|---|
| `id`, `name`, `spriteUrl` | **1** — id and sprite are derivable from the list |
| `+ types[]` | **150** — types only exist on detail |
| `+ stats`, `height`, `weight` | still 150, same calls |

Since types come free once you're already making 150 calls, and they make the UI visibly better (type badges, filtering — natural pairing-session extensions), I'd take them:

  name: string;       // 'charizard' — lowercase from the API; title-case in the UI

## 2. Seed data in the migration — your instinct is defensible

I steered away from this in the first draft, and I want to correct that: **my objection only applies if the migration makes the network call.** With the JSON committed to the repo, a migration is deterministic, offline, and rollback-able. Static reference data is genuinely one of the accepted cases for seeding via migration.

| | Seed inside a migration | Separate seed step |
|---|---|---|
| Setup | `migration:up` does everything — one command | Needs its own Tilt resource + npm script |
| Determinism | Locked to schema version, rolls back cleanly | Can drift out of sync with schema |
| Re-seeding | Needs a new migration | Just re-run it |
| Fits the data | ✅ 150 immutable reference rows | Better for mutable/demo data |
| Reviewer signal | Reads as "understands reference data" | Reads as "separated concerns" |

## 3. The 6-max constraint — where it belongs

Short answer: **all three layers, but they are not redundant — each answers a different question.**

**Frontend — "what can I do right now?"**
Pros: instant feedback, no round-trip, disable the 7th card and gray the grid when full. This is the difference between usable and annoying.
Cons: trivially bypassed (devtools, direct API call). Stale if two tabs are open. **It is an affordance, never enforcement** — treating it as the guarantee is the classic mistake.

**Backend — "is this request valid?"** ← *the authority*
Pros: single enforcement point for every client. Where the 400 and the readable error message come from. Testable in isolation — this is where your Vitest specs earn their keep. Can express rules the DB can't (unknown-Pokémon-id, ownership).
Cons: still race-able under concurrent requests unless the check and write share a transaction.
**If you only did one layer, it's this one.**

**Database — "can this state exist at all?"**
Pros: survives application bugs, concurrent writes, manual SQL, and future services that skip your service layer. The one guarantee that doesn't depend on code being correct.
Cons: errors surface as constraint violations that need translating into decent HTTP responses; a naive implementation means a trigger or count query on every write.

**But here the `slot` column makes it nearly free.** You don't need a trigger:

```sql
slot smallint NOT NULL CHECK (slot BETWEEN 1 AND 6),
UNIQUE (profile_id, slot),
UNIQUE (profile_id, pokemon_id)
```

Six legal slot values, each usable once per profile ⟹ **a 7th row is structurally impossible.** No counting, no trigger, no write-path cost. That's the strongest argument for the explicit join entity over MikroORM's implicit `@ManyToMany` pivot — the pivot table has no `slot` column, so the cap would have to be a trigger instead.

So: **DB guarantees it, backend enforces it with a good error, frontend prevents you from trying.** Three layers, three jobs, no duplication of responsibility — and it's exactly the kind of reasoning the README says they're grading.

**1. Seed provenance — you already get part of it free**

`mikro_orm_migrations` records `executed_at` per migration, so "when was this data applied" already exists with zero work.

What's missing is when the data was *fetched* from PokéAPI. Three tiers:

| Option | Effort | Gives you |
|---|---|---|
| Metadata header in the committed JSON — `{ fetchedAt, source, count, pokemon: [...] }` | ~5 min | Provenance visible in git diff |
| `+ imported_at` column on `pokemon` | ~10 min | Per-row, queryable |
| `seed_metadata` table (`source`, `source_version`, `fetched_at`, `row_count`) | ~30 min | Real versioning, supports future re-imports |

**MVP: take the JSON header.** Five minutes, no schema cost, and it answers your question ("what version of the data is this") directly in the repo. The `seed_metadata` table is the right answer once data actually refreshes — defer it, note it in `ARCHITECTURE.md`.

**2. Making the 6 configurable — cheap in code, a migration in the DB**

| Layer | Effort to change | Notes |
|---|---|---|
| Backend | ~10 min | Read from config/env |
| Frontend | ~20 min | Must come *from the API*, not a second hardcode |
| **Database** | **needs a migration** | `CHECK (slot BETWEEN 1 AND 6)` bakes it into the schema |

The DB is the catch — and it's the same design that made the cap free. Raising it (6→10) is a safe one-line migration. *Lowering* it is a data migration, because you must decide what happens to teams already over the new limit.

The fix that costs nothing now: **export `MAX_TEAM_SIZE = 6` as a single const from `pokemon-contracts`.** Backend validation and frontend UI both import it, so the number is hardcoded in exactly **two** places total — that const, and one migration file. Changing it in prod becomes a ~30-minute task, not a refactor.

That's not architecture debt; it's a documented one-liner. Genuine config-param treatment (per-profile limits, runtime-adjustable) means dropping the `CHECK` and giving up the DB guarantee — a real tradeoff, and not one worth making for a game rule that hasn't changed since 1996.

## 31. Prompt

I didn't understand why " 'UNKNOWN_POKEMON' // 400 — id in the body, not the path, so not a 404"

---

## 31. Response

The distinction is about *where* the bad id lives, and what 404 conventionally promises.

`PUT /api/profiles/:id/team` has two different ids in play:

- **`:id` in the URL path** — identifies the resource the request is *addressed to* (the profile). If that doesn't exist, 404 is correct: the URL points at nothing.
- **an id inside `pokemonIds` in the JSON body** — one entry in the payload happens to reference a Pokémon that doesn't exist. The *URL is fine* — the profile it points to is real. The body is just malformed data.

404 means "the thing this URL addresses isn't there." Returning 404 for a bad body value would incorrectly suggest the profile itself vanished, when actually the profile exists and the request failed for a different reason — a bad reference inside the payload, which is a 400 (bad request) situation.

So: `PROFILE_NOT_FOUND` → 404 (path id, addresses the resource). `UNKNOWN_POKEMON` → 400 (body id, just invalid input).
